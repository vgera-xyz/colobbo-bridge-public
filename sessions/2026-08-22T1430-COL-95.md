## The two re-scopes

**1. Auth: service-account API key → per-user OAuth2.** Operator: *"we are a saas product so like you can use linear based on your permission similar."* The customer signs in as themselves; their own permissions decide what they see.

Researched against the [published MCP authorization spec](https://modelcontextprotocol.io/specification/draft/basic/authorization) rather than memory. The binding constraint: an MCP server **MUST** validate tokens were issued for it as audience and **MUST NOT** accept or transit others. Colobbo pins one shared Cognito `clientId`, so web, mobile and a customer's AI client are indistinguishable — reusing the web token is exactly the passthrough anti-pattern the spec prohibits. That promoted [COL-508](https://linear.app/colobbo/issue/COL-508) from modernization nicety to hard dependency (raised to High).

Design: dedicated app client + resource-server scopes; `api_node` accepts an audience array (`aws-jwt-verify@5.2.1` types `clientId` as `string | string[] | null`, verified in `cognito-verifier.d.ts:13,110`) and enforces the `scope` claim it currently never reads; RFC 9728 metadata endpoint. Existing per-user scoping does the rest.

**2. Vendor lock-in: single-model → vendor-independent.** Operator: *"we are independent of vendor lockin and can work with all."* My prior recommendation (ship one model, defer multi-provider) assumed single-vendor was the default and was wrong. Rewritten — and it revealed that **selling questions rather than tokens is what makes multi-vendor commercially viable**: a token is neither the same unit nor the same price across providers, so token-denominated credits would drain at a rate the customer can neither see nor control.

Consequences recorded: evals move from optional to **required**; the data-protection promise becomes the **intersection** of every vendor routed to, not the best one; Portkey moves from optional to the default routing choice, subject to resolving its own retention posture first.

## Fourth cross-tenant read — and the AI feature is not greenfield

Verification found `POST /api/ai/chat/init` and `/ai/chat/:chatId/message` already shipped: a **document chat widget** on Documents Upload, routed under the side menu, running **OpenAI** (`openai@^4.56.0`), sessions in process memory, behind `AI_ENABLED` (default `false`).

`aiController.ts:4-9` takes `companyId` **from the request body** and passes it to `rebuildCompanyContext(companyId)` with no check against `req.user`. **[COL-655](https://linear.app/colobbo/issue/COL-655) filed Urgent** — materially worse than its three siblings because it is a retrieval system: it reads another tenant's documents and *summarises the answer in plain English*. Sessions also carry no owner, and `chatId` is `Date.now()` + `Math.random()`.

**Step 0 for any build session: confirm whether `AI_ENABLED` is true in production.** That decides live vs latent, and needs prod env access this tooling does not have.

## Metering — credits, not seats

Operator requirement: company can pay; external subcontractors are individuals who self-fund; internal users can self-fund *or* request organisation access; top-ups go to an individual or a shared pool; there must be a usage limit; **per-seat is rejected**.

Design ([COL-654](https://linear.app/colobbo/issue/COL-654)): a balance owned by a company or a user, spent in a **fixed order — company pool first, personal second**.

**This reversed my own earlier call.** I first made funding exclusive (`company` XOR `self`) and argued against a fallback chain. That objection was about *ambiguity*, not ordering, and the exclusive model failed the requirement outright — a user with a company allowance could not top up without surrendering it. A fixed, stated order is not ambiguous.

Company access is per **membership** (`tblUserCompany` has no unique constraint on `userId`; `api_node` already switches tenancy on `selectedCompanyId`); the personal balance is per **user**, so a subcontractor working three companies buys credits once.

Credits denominated in **questions**, not tokens. Prepaid credits *are* the limit. Stripe: two object types, every grant idempotent on the event id. **No Stripe dependency exists in `api_node` today** — verified, greenfield.

## Pricing deliberately deferred

Operator: *"we are worrying about something that can be done later — you need to think about what is logical first."* Correct. I had produced a cost-per-question table whose *prices* were verified but whose *shape inputs* (3k cached, 5k fresh, 3 calls/question) were invented.

**Recommended sequencing: build with metering on and billing off**, read a month of real data, then price against comparable products. Small change to the order of work, large gain in defensibility.

## The gap nobody has closed

Raised and still open: **there is no user story.** The spec covers auth, tenancy, metering, guard rails, failure modes — and not one statement of what the feature is *for*. Which means the six tools were chosen for being *safe*, not *useful*; a question's worth is unknowable; and the eval question has no owner because there is no success metric. Fin has a sharp one (deflect tickets, measured as resolution rate). Colobbo's does not.
