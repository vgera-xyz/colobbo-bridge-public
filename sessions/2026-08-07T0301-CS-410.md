## Summary

Built and shipped the **version-bump gate** across both active product repos, hardened the release/hotfix gate state, and captured the durable release-process gotchas we rediscovered. Canonical operator session; direct pushes to `colobbo-agent-system` main; product-repo changes via PR only.

- **version-bump gate (new):** blocks any PR into `staging`/`main` unless the version is **higher than `main`** — checked against `main` (not `staging`) so bug-fix re-promotes keep one number and still pass, while a forgotten bump collides with `main` and fails at the first promotion. Pairs with `auto-tag-release.yml` (bump enforced, tag automatic). Rejects non-semver strings; api_node variant also rejects out-of-lockstep app versions. Validated locally: YAML parse, actionlint clean, semver guard + numeric compare unit-tested.
- **Merged (product repos):** api_node **#438** (version-bump → `development`), web-angular **#696** (version-bump → `development-stage`), web-angular **#688** (auto-tag → `development-stage`). api_node auto-tag (#427) was already merged.
- **Branch protection — `release-source` now REQUIRED on all 4** (api_node `staging`+`main`, web `staging`+`main`); operator toggled `staging` on both + web `main` this session. **`version-bump` is NOT yet required anywhere** — its workflow file is only on the integration branches, so it never ran, so the GitHub UI won't list it yet (add via API, or after the first release runs it once).
- **Sentry verified fully wired:** all 9 org **variables** present (`SENTRY_ORG`, api/notification/web/mobile dev+prod pairs) + `SENTRY_AUTH_TOKEN` secret. A mid-session "notification-prod variable missing" alarm was a **false positive** (paginated/incomplete list read) — corrected by authoritative direct GET; nothing was created.
- **Docs:** refreshed the first-release/hotfix preconditions in `wiki/architecture/release-process.md` with origin-verified 2026-08-07 state (replacing the stale 2026-07-19 "4-of-7 / 0-of-7" numbers) + two lessons: auto-tag isn't on either `main` until the first release (pre-first-release hotfixes tag by hand); prefer a first *release* over a hotfix on a repo that has never released.

## Verified gate/release state (origin, 2026-08-07)

- **No first release has happened** in either repo: api_node apps all `1.0.0`, web `0.0.0`, **zero `vX.Y.Z` tags** anywhere.
- **api_node hotfix lane works today** — all four required-check workflow files (`gates-changed`, `pdf-lambda-artifact`, `typecheck`, `release-source`) are on `main`, and `release-source` waves `hotfix*` through. `auto-tag-release.yml` is NOT on api_node `main` → a pre-first-release hotfix must be tagged by hand.
- **web-angular hotfix strands on `release-source` alone** — that check is required on web `main` but `release-source.yml` isn't in web `main`'s tree (all other required-check files are). A hotfix branched from web `main` never runs it → "waiting for status" forever. Clears when the first release carries the file up, or via temporary un-require.
