## Summary

Built the brownfield safe-modify capability, scored it through two calibration rounds, and opened the competence boundary on a 10/10. Then found the gap that makes the opening narrower than it looks.

**The proven ground is one insertion into one file. Almost no real ticket is that shape.** Multi-file safe-modify is not an extension of this capability — it is what makes it usable at all, and it is blocked on a defect found after the boundary was opened.

## The capability

The model never writes the file. It emits an anchored plan — `{file, anchor, position, text}` — and `scripts/apply-safe-modify.mjs` performs the insertion, then proves the original survived by checking it is still a **subsequence** of the result. `minimal_diff` stops being a property a judge scores and becomes one the applier enforces.

Four refusals, each stating its reason: an anchor matching zero or many lines, a path on the auth/tenancy denylist, inserted text naming a denied token, caps exceeded. Auth and tenancy are **permanently** human-owned — not a v0.1.0 limit awaiting confidence.

## The gap that now leads the queue

**The applier has no plan-level atomicity.** It writes each file as it goes, so a plan whose third file is refused leaves the first two modified — exit 3, tree half-changed. Verified empirically at handoff time.

The per-file guarantee (additive-only, subsequence-verified) holds. There is no plan-level guarantee at all. It did not bite here only because a route registration is two insertions in **one** file.

Required: all-or-nothing application, or an explicit refusal when a multi-file plan cannot be applied atomically.

**Order matters and is operator-set: fix atomicity, then write the multi-file case, then COL-686.** A case written against the current applier would score partial application as acceptable and bake the defect into the specification.

## Two calibration rounds

**Round 1** yielded one clean disagreement from four criteria — `minimal_diff`, operator 2 against builder 3 — and the builder lost it. The builder's first response was to argue the criterion conflated two concerns and needed redesign; the operator rejected that, and the record was corrected to say so. **The rubric survived contact; the builder's calibration did not.**

Round 1 also leaked three ways, now named in [[../../patterns/eval-blinding-leaks]]:
1. **In-artifact self-justification** — the candidate wrote a code comment asserting its own placement was correct. Blinding says grade from artifacts not self-report, but the self-report was *inside* the artifact and could not be withheld. The criterion that would have replaced that assertion with evidence, `runtime_behaviour`, was the one round 1 could not produce.
2. Builder scores reaching the operator first, contaminating two criteria of four.
3. Questioning the measure instead of the measurement.

**Round 2** ran against a bootable scratch checkout with commit-reveal sealing. Both sets sealed before either was disclosed, digest verified on open, **operator and builder unanimous at 3/3/3 — 10/10**. The row records `ensemble: false`, and Gate 27 states beside any boundary opened on it that no ensemble scored it. Agreement between the operator and the builder of the applier is weaker evidence than a disagreement would have been.

## A false-green class worth naming

Writing the test that proves `no_unactioned_skips` **can fail** immediately found a false-green inside the applier — the tool built to prevent them.

Idempotency was a **substring match on the joined file**. Inserting `x` into a file already containing `const app = x();` reported `already_present` and silently did nothing, while the run reported success. In production that drops a legitimate insertion and calls it applied.

The general shape: **a check whose success condition can be satisfied by an unrelated coincidence.** Substring where a structural match was meant. It was invisible until a test demanded the criterion be capable of failing — the operator's condition, `if it can't fail, don't ship it`, which is what produced it.

## Gates and thresholds set before the numbers

The Gate 27 bar was written into glaze **dated before any score existed**: min 8.0, with `runtime_behaviour` and `no_unactioned_skips` required at maximum and checked **independently of the weighted total**. A mean lets a failure on the load-bearing criterion be paid for with cosmetic ones. Proven: 8.7 with `runtime_behaviour` at 2 is refused. No tolerance band — a band is a discretion hole exercised by whoever wants the capability opened.

Also: per-case criterion lists with weights **not** renormalised (renormalising makes a 7 on one case mean something different from a 7 on another while presenting the same scale), and `scoring_provenance` as a required structured field.

## Corrections taken

- **The README described a blinded ensemble that does not exist.** `eval-record` takes judge scores as an input; nothing produces them. Round 1 was scored operator-versus-builder with the builder standing in, unlabelled. Documentation asserting a capability nothing implements is the same class as a green job that rebuilds nothing. Corrected; [CS-426](https://linear.app/colobbo/issue/CS-426) filed to build it.
- **CS-329 was not a dependency.** Filed as "probable hard dependency" on a guess; insertion-only edits need only what is readable in the target file, and no such lobe exists.
- Three bugs in `eval-scratch.sh` on first use, and [COL-692](https://linear.app/colobbo/issue/COL-692) — the merged harness resolves its app directory through a fixed four-level walk that only works from the repo root.

## What's next

1. **Applier plan-level atomicity** — all-or-nothing, or refuse a multi-file plan outright. Leads the queue.
2. **A multi-file eval case**, written after the fix, never before.
3. **COL-686** — dispatched and cancelled at handoff; it stays the first real ticket.
4. [CS-426](https://linear.app/colobbo/issue/CS-426) blinded ensemble, before a second case.
5. [COL-692](https://linear.app/colobbo/issue/COL-692) harness portability — upstream still has the bug; only the scratch copy was patched.

**Open question for the operator:** `competent_on` now lists `safe-modify`, which claims ground broader than one-file plans. Consider capping `glaze.safe_modify.max_files_per_plan` at 1 until atomicity lands, so the claim matches what is proven.
